## Low-hanging fruit

The ten most valuable fixes that each take under a day. Items 1 to 5 and 7 have tested patches ready.

1. **The app should follow the reading generation the speech service returns** (finding R1). Today it guesses from positions, and a reading that starts at a skipped code block never moves the highlight and never ends. Patch `s1-reading-generation.patch`. Owner D3 (`textweaver-app`). Small.
2. **Plan continuous reading in windows, not to the end of the document** (finding P1). Every Read, every jump while reading, and every resume plans the whole rest of the document on the UI thread. Patch `s3-plan-reading-in-windows.patch` (on top of S1). Owner D3. Small.
3. **Make F9 and the `character_keys` setting work** (finding A1, WCAG 2.1.4), and give Shift+arrows (select) and Shift+S (read paragraph) their handlers (finding A2). Patch `s2-single-keys-and-missing-actions.patch`. Owner D3. Small.
4. **Draw the highlight as soon as it arrives** (finding R3). The terminal loop applies speech status, then waits up to 40 ms for a key before drawing. Patch `s4-tui-loop-highlight-latency.patch`. Owner D3. Small.
5. **Quitting in edit mode after a save loses bookmark and note positions** (finding D1). Patch `s5-quit-after-save-rebuilds.patch`. Owner D3. Small.
6. **Speak the first item when a list opens, with "1 of 5"** (finding A4). Today the first bookmark, note, or choice is never heard unless you press Up. Owner D3 (`textweaver-tui`, with an `announce_queued` in the app). Small.
7. **Use the `table_mode` setting** (finding G2). Tables always read "structured". Patch `s6-table-mode-setting.patch`. Owner D3. Small. With it, patch `s7-ordered-list-item-text.patch`: jumping to an ordered list item says "2. Walk the dog", not just "2." (finding A6).
8. **Enable GFM task lists and keep the text of HTML blocks** (findings M1, M2). `- [ ] item` reads its brackets; `<details>`, `<p align>` and inline HTML text vanish. Owner A2 (`textweaver-formats`). Small.
9. **Refuse binary files and decode UTF-16 and Windows-1252 on load** (finding D3). A `.docx` or `.pdf` without its loader is read aloud as garbage; UTF-16 text reads letter by letter. Owner A2. Small to medium.
10. **Detect files changed on disk before saving** (finding D2). Editing a note that Obsidian, VS Code, or `git pull` also changed overwrites their changes without a warning. Owner C and D3. Small to medium.

Close behind: a log file (finding D5), a faster Edit mode toggle on large files (finding P3), and a short guide to using the terminal reader with JAWS or NVDA (finding G6).

## What this branch fixes

Each fix is its own commit with a test. Crates: `textweaver-text`, `-speech`, `-core`, `-store`, `-editor`, `xtask`, and CI.

1. **Sentence segmentation was quadratic in a paragraph's line count** (commit `1ca5b4c`, `crates/textweaver-text/src/units.rs`). Hard line breaks were looked up with `Vec::contains` for every line break. A tight list is one paragraph, so a 50,000-line list took 6 seconds to plan and 6.8 seconds per next-sentence key. Test: `a_long_tight_list_is_one_sentence_per_item`.
2. **Every narrated sentence scanned every earlier table row and code block** (commit `dc78a23`, `crates/textweaver-text/src/marker.rs`). `MarkerIndex::enclosing` scanned all markers of a kind before the position; narration calls it for every sentence, so planning grew with sentences times table rows. It now stops as soon as no earlier marker can reach the position. Property test: `enclosing_with_tables_matches_a_full_scan`.
3. **Sentences are segmented one run of lines at a time** (commit `b89a22a`). A sentence never crosses a hard break, so a sentence step or a highlight update in a long list no longer segments the whole list. Property test: `sentence_runs_agree_with_whole_paragraphs`.
4. **An engine that keeps failing no longer floods the app with errors** (commit `52109c5`, `crates/textweaver-speech/src/service.rs`). A failed `speak` used to be followed by the next sentence at once, through the whole document inside one call, with one error per sentence. The reading now stops after three failures in a row, and an error repeated within three seconds is reported once. That also ends the loop in which the app voiced "Speech error" through the failing engine forever. Tests: `an_engine_that_always_fails_stops_the_reading_once`, `a_repeated_error_is_not_reported_again_within_the_window`, `a_host_crash_failing_queued_utterances_is_reported_once`.
5. **Rate, pitch, and volume changes while reading are heard at once** (commit `c952498`). Eloquence and SAPI have no live rate: the playing sentence and two lookahead sentences were already synthesized, so a new rate was heard two or three sentences later. The service now restarts from the last confirmed word, as it does for an announcement, on engines that report words (commit `755580f` leaves timer-paced engines such as Omnivox alone until the app follows reading generations, patch S1). Tests: `a_rate_change_while_reading_is_heard_from_the_current_word`, `parameter_changes_while_idle_or_paused_restart_nothing`.
6. **A corrupt per-document state file is set aside, not overwritten** (commit `6a54494`, `crates/textweaver-store/src/doc_state.rs`). An unparseable file counted as "no state", and the next position save (every 30 seconds) replaced it, losing that document's notes, bookmarks, and highlights. It is now renamed to `<key>.corrupt-<time>.bak`, and pruning no longer deletes unparseable files first. Test: `a_corrupt_state_file_is_set_aside_not_overwritten`.
7. **Recent files are stored resolved; an empty `TEXTWEAVER_HOME` is ignored** (commit `ccae825`). `textweaver notes.md` left a relative entry that did not open from another folder. An empty variable put `config/`, `data/`, and `cache/` in the current folder. Tests: `relative_and_absolute_paths_are_one_resolved_entry`, `an_empty_home_override_is_ignored`.
8. **Saving protects the file** (commit `0366d6c`, `crates/textweaver-editor/src/autosave.rs`). Save wrote a temp file and renamed it over the path as given. A symbolic link became a plain file (the real file stopped getting updates), Unix permissions reverted, and a read-only file was overwritten. A Windows-1252 or UTF-16 file, read with replacement characters, was saved with them for good. Links are now written through, permissions kept, and read-only and non-UTF-8 files refused with a message suggesting Save As. Tests: `save_text_refuses_read_only_and_non_utf8_files`, `save_text_writes_through_links_and_keeps_permissions` (Unix).
9. **A reversed range in a state file can no longer panic** (commit `a164bd2`, `crates/textweaver-core/src/pos.rs`). `CharRange` deserialized without ordering its ends; `len()` underflowed and ropey's slice panicked. Test: `deserializing_orders_endpoints`.
10. **`cargo xtask bench`** (commit `aa564df`, `xtask/src/bench.rs`), described below.
11. **CI** (commit `200a03a`): pushes to `wave*/**` and `integration/**` branches now run CI, and Windows and macOS build and test the Omnivox backend.
12. **A corrupt `recent.json` is set aside too** (commit `e8f5870`), with the same helper as the state files. Test: `a_corrupt_recent_list_is_set_aside`.
13. **Classic Mac line endings survive a save** (commit `3663873`). Files with CR-only line breaks were saved with LF. Test: `save_text_keeps_classic_mac_line_endings`.

## Findings

### Speech and highlighting reliability

**R1. The app guesses which reading a status belongs to, and can get stuck in "Reading".** High. Owner D3. Small; patch S1.
- Evidence: `crates/textweaver-app/src/playback.rs:208` discards the `ReadingGeneration` that `SpeechService::read` returns (`crates/textweaver-speech/src/service.rs:362`). `SpeechTrack` (`playback.rs:41-151`) accepts a new generation only if its first position touches the first utterance's range (`playback.rs:123`) and otherwise rejects the whole generation (`playback.rs:129`). Its comment says the contract gives the app no generation, which is no longer true.
- Failing case, reproduced by the test in the patch: with `skip_code` on (the default, `crates/textweaver-store/src/settings.rs:212`), reading from the blank line before a code block starts with "code block skipped", anchored at the code block (`crates/textweaver-text/src/narrate.rs:215`). The next sentence does not touch that anchor, so every position is rejected: the highlight never moves, `Finished` is ignored, and the app stays in Reading. While it thinks it is reading, polite announcements are not spoken (`crates/textweaver-app/src/app.rs:409`), so "No next heading" and the like go silent until Stop.
- A second case: an assertive message during a reading makes the service restart one word back on timer-paced engines (`service.rs`, `resume_point`); a position before the last accepted one rejects the rest of the reading.
- Fix: keep the generation `read` returns and accept a status only when its generation matches. The patch replaces `SpeechTrack` with that and adds `tests/reading_generation.rs`.

**R2. A failing engine looped forever.** High. Service half fixed (commit `52109c5`); app half owner D3, small.
- Evidence: `ServiceCore::pump` cancelled a failed utterance and went on to the next one in the same loop (`service.rs`, `pump`), so a missing or hung Eloquence host failed every remaining sentence in one call; each failing `speak` can wait up to 10 seconds per host candidate (`crates/textweaver-eci/src/backend.rs:49`, `:609`). The app turns each `BackendError` into an assertive announcement (`playback.rs:476-479`), which it speaks through the same engine (`app.rs:410`), which fails again.
- Fixed in the service: the reading stops after three failures in a row, and an error repeated within three seconds is reported once.
- Still worth doing in the app (small, lower priority now that the loop cannot happen): send speech errors to the status line and the announcer rather than speaking them through the engine that failed, and name a way out in the message (another voice, or `--backend null`).

**R3. The highlight is drawn up to 40 ms late, sometimes 80 ms.** Medium. Owner D3. Small; patch S4.
- Evidence: `crates/textweaver-tui/src/lib.rs:47-60` draws, then applies speech status (`tui.tick()` calls `poll_speech`), then waits up to 40 ms for a key. A word applied in `tick` is drawn only after that wait. The hardware cursor, which JAWS follows, moves at the same time.
- Fix: apply status before drawing, and wait 10 ms instead of 40 while reading. A later step is a thread that forwards terminal events and speech statuses into one channel, so the loop wakes on either.

**R4. An Eloquence host crash skips the rest of the sentence and the lookahead.** Medium-high. Owner H/B2 (`textweaver-enginehost`, `textweaver-speech`). Medium.
- Evidence: `Playback::host_died` fails every utterance the host still owed (`crates/textweaver-enginehost/src/playback.rs:359-373`); the service completes each and moves on (`service.rs`, `handle_event`). Up to three sentences are never read. (The error is now reported once, not three times.)
- Fix: treat a host failure like an emulated pause: restart from the last confirmed word with a new generation, retry once, then stop with a clear message. Test with the recording backend in manual mode: deliver a word, then `Error` and `Finished` for the queued chunks, and check that the next utterance resumes at that word.

**R5. No watchdog when audio stops playing.** Medium. Owner H. Small.
- Evidence: word and finish events come only from samples consumed by the audio device (`crates/textweaver-enginehost/src/playback.rs:399-403`). The stall detector watches the host only while it owes audio (`crates/textweaver-enginehost/src/process.rs:189`). If the device stops pulling samples (a Bluetooth headset disconnects), the reading stalls with no error and the app stays in Reading.
- Fix: if a reading is playing, not paused, and consumption has not moved for a few seconds, report an error and stop.

**R6. On macOS, AVSpeech highlights may lag by the latency offset (120 ms).** Low for Jon. Owner F/B2. Tiny, but verify on a Mac.
- Evidence: the backend emits each word when playback reaches it (`crates/textweaver-apple/src/macos/avspeech.rs:641-661`) but does not declare `PLAYBACK_EVENTS` (`:748-755`), so the service schedules it again at audio time plus the latency offset (`service.rs`, `handle_event`). ADR-0012 fixed the same thing for SAPI.

**R7. Smaller speech items.**
- When word events resume after the timer ran ahead, the highlight can jump back one word (`service.rs`, `confirm` repaints unconditionally). Low.
- Offset-map invariants are checked only in debug builds; `trim_utterance` falls back to an empty map, which silently loses the highlight for that utterance. Low.
- SAPI treats a silent host as hung only after 60 seconds (`crates/textweaver-sapi/src/backend.rs:70`). Low.
- The first speech after start is about 20 to 50 ms slower than later speech (the first normalization builds its rules); it could be warmed at spawn. Low.

What looks solid: generations inside the service (bumped before every stop and restart, stale events dropped at the sink), unbounded channels with no busy loop, offset-map composition (property-tested), UTF-16 positions from SAPI, espeak's character positions, Eloquence index marks, and the engine-host crash and restart tests.

### Speed

**P1. Every Read, jump while reading, and resume plans the whole rest of the document.** High for long documents. Owner D3. Small; patch S3. Numbers in the benchmark section.
- Evidence: `read_from` reads `start..end of document` (`playback.rs:221`), and `read_range` calls `textweaver_text::plan` on it (`playback.rs:200`) on the UI thread. `plan` collects every sentence up front (`narrate.rs:121-127`). Navigation while reading calls `read_from` again (`follow_jump`, `playback.rs:241`), and resume re-reads (`playback.rs:286`).
- Fix (patch S3): plan 32,768 characters at a time, ending at a sentence end and never inside a table or code block, and read the next window when the service reports `Finished` for this one. A window is about ten minutes of speech; the pause between windows is one engine start. A better long-term fix is a service call that appends to the current reading, so the lookahead never drains.

**P2. Sentence units in one-line documents are slow.** Medium. Owner: `textweaver-text`. Medium.
- Evidence: in a 1 MB file with no line breaks, next sentence takes about 60 ms and a highlight update up to 140 ms (benchmark `one-line-1mb.txt`), because the whole line is one run of text to segment. Runs cannot be split safely without a line break; a window with overlap, checked against the whole-line result by a property test as the word windows are, would fix it.

**P3. Entering and leaving Edit mode on a large file is slow.** Medium. Owner D3 (`align.rs`, `edit.rs`) with A2. Medium.
- Evidence: entering Edit mode takes 50 to 270 ms on 1 MB and 0.5 to 2 s on the 50,000-line list, with 157 MB peak heap (benchmark, several runs). `Aligner` builds a lowercase `String` for every word of both texts (`crates/textweaver-app/src/align.rs:24-47`), and `enter_edit` reads the file again and copies the text twice (`edit.rs:259-305`).
- Fix: store words as ranges and hash them instead of allocating strings; better, have the Markdown loader record source offsets for each canonical span, so positions map exactly (see M4).

**P4. Loading is single-pass but allocation-heavy.** Low-medium. Owner A2. Medium.
- Evidence: 10 MB loads in about 400 ms with 72 MB peak heap for 29 MB retained. `load` makes the bytes, a lossy string, two `replace` copies, then the rope (`crates/textweaver-formats/src/lib.rs:238-242`).

**P5. Autosave and position saves block the UI thread.** Low-medium. Owners: `textweaver-editor`, `textweaver-store`, D3. Medium.
- Evidence: a recovery snapshot of a 5 MB file takes about 30 ms (benchmark), and a single write took 324 ms once on this machine (fsync and the virus scanner on a new temp file). Position saves take 2 to 3 ms, and 150 ms for the first one. All run in `App::tick` on the UI thread (`app.rs:709-734`, `crates/textweaver-editor/src/session.rs:500-526`).
- Fix: a writer thread that takes the latest snapshot or state and writes it, reporting errors on the next tick.

**P6. Other costs worth knowing.** Find copies the whole document into a string each time (`crates/textweaver-text/src/search.rs:110`), about 8 ms on 5 MB. The terminal draws every loop even when nothing changed, and wraps the whole current line each time (`crates/textweaver-tui/src/layout.rs:111-113`), which matters only for very long lines.

### Accessibility

**A1. Single-key shortcuts cannot be turned off (WCAG 2.1.4).** High. Owner D3. Small; patch S2.
- Evidence: F9 is bound to `toggle_character_keys` (`crates/textweaver-keymap/src/action.rs:375`), but `run_action` has no arm for it and says "... is not available yet" (`app.rs:1029-1031`). The `[keyboard] character_keys` setting is never read: `build_app_with` builds the keymap without it (`crates/textweaver-tui/src/setup.rs:125-142`). The extra note keys (`'`, `"`, Shift+Y) bypass the keymap (`crates/textweaver-app/src/extra.rs`). README, CHANGELOG (alpha.3), and `docs/keyboard.md` promise it.
- The patch applies the setting when the app starts, handles F9 (announced assertively, saved), makes the extra keys respect it, and adds a test that every action with a default key has a handler.

**A2. Shift+arrows, Shift+S, Alt+V, and Alt+L say "not available yet".** High for authoring. Owner D3. Small (select, read paragraph); medium (voice chooser, library).
- Evidence: actions without an arm in `run_action`: `SelectNextWord`, `SelectPreviousWord`, `SelectNextLine`, `SelectPreviousLine`, `ReadParagraph`, `ChooseVoice`, `OpenLibrary`, `ToggleCharacterKeys`. The keymap binds Shift+arrows in Browse (a test asserts it, `crates/textweaver-keymap/src/keymap.rs:768-773`), so the TUI's own fallback for them (`crates/textweaver-tui/src/ui.rs:287-298`) never runs. Without a selection, Read selection and Highlight selection cannot be used in Browse mode.
- The patch handles selection and Read paragraph.

**A3. While reading, navigation at a boundary is silent except for an earcon.** Low. By design the reading is the feedback, and "No next sentence" goes to the status line only (`app.rs:409`). The boundary earcon plays only on engines with tones (Eloquence and SAPI have them). Worth a note in the guide.

**A4. The first item of a list is never spoken.** Medium. Owner D3. Small.
- Evidence: `Effect::ShowList` announces nothing (`ui.rs:162-175`); the app's intro ("Bookmarks, 3 items. Enter goes to one...") does not name the selected item, and moving down speaks item 2. Items carry no "2 of 5".
- Fix: when a list opens, queue (not interrupt) "1 of N: first item" after the intro; say "k of N" on each move. The app needs an `announce` that queues (today every announcement uses `SayMode::Announce`, which interrupts the previous one).

**A5. A repeated message does not reach a screen reader.** Medium when running with `--no-speech`. Owner D3. Small.
- Evidence: `StatusLineAnnouncer::seq` changes on every announcement so a frontend can show a repeat (`crates/textweaver-a11y/src/lib.rs:207-231`), but the TUI never reads it. Pressing Next heading twice at the end shows the same "No next heading." and JAWS says nothing the second time.
- Fix: blank the status line for one frame, or append a changing marker, when `seq` changes and the text does not.

**A6. Jumping to an ordered list item says only its number.** Medium. Owner D3. Small.
- Evidence: `marker_content` returns the marker's label ("3.") instead of the item text (`crates/textweaver-app/src/nav.rs:252-255`), so the user hears "List item: 3.".
- Fix: the label followed by the preview.

**A7. Some failures are only logged, and nothing is logged anywhere.** Medium. Owner D3. Small. See D5.

**A8. The announcement catalog is not what the app says.** Low. Owner D3 with C. Medium. The `Announcement` catalog and its verbosity table (`crates/textweaver-a11y/src/announce.rs`) are used only by `tw library`; the app writes its own strings, and some key hints are spoken at Normal verbosity ("Edit mode on. Save: ... Finish: ..."), where the a11y rules put key hints at High.

What works: the hardware cursor follows the spoken word, the caret, the Speech Cursor line, the prompt caret, or the selected list row; key presses are filtered to Press and Repeat, so nothing acts twice on Windows; keys are remappable through `keymap.toml` with conflict warnings.

### Markdown reading and authoring

**M1. Task lists are not recognized.** Medium. Owner A2 (formats) and text (narration). Small.
- Evidence: the parser options (`crates/textweaver-formats/src/markdown.rs:60-65`) lack `ENABLE_TASKLISTS`, so `- [ ] Buy milk` reads "left bracket right bracket Buy milk" (depending on punctuation level) and the `TaskListMarker` arm (`:252`) never runs. `ENABLE_MATH` is also off, so the `InlineMath` arm is dead; GFM alerts (`> [!NOTE]`) and heading attributes (`{#id}`) are read as text.
- Fix: enable the options and speak "done" or "not done" through the list item's label.

**M2. HTML blocks and inline HTML are dropped.** Medium. Owner A2. Medium.
- Evidence: `Event::Html` and `Event::InlineHtml` keep only `<br>` (`markdown.rs:245-250`). README-style `<p align="center">Welcome</p>`, `<details><summary>...` text, and inline `<img alt>` vanish without a sound.
- Fix: strip tags and keep text; turn `<img alt>` into an Image marker.

**M3. Structure the reader cannot hear.** Low-medium. Owner A2 and text. Small each. Strikethrough has no marker (`markdown.rs:370`), so deleted text reads as normal text; thematic breaks have no marker (`:244`); nested lists say "list with 3 items" but never their depth (`narrate.rs:239-242`).

**M4. Edit mode has no structure, and positions cross between source and reading by word alignment.** Medium. Owners D3 and A2. Medium to large.
- Evidence: Edit mode holds `Document::from_plain_text` (`crates/textweaver-app/src/edit.rs:292-296`), which has no markers, so heading, list, link, and table navigation say "No next ..." while authoring. Positions move between the Markdown source and the canonical text through `Aligner`, a greedy word match with a 64-word lookahead (`align.rs:50`); front matter or link URLs that add more than 64 words before the first shared word defeat it, and positions fall back to "the same fraction of the text".
- Fix: have the Markdown loader record source offsets (pulldown-cmark's `into_offset_iter`) as an offset map from canonical to source; use it for Edit mode positions and to build markers in source coordinates, re-parsed when typing pauses.

**M5. Footnote reading mode is stored but not used.** Medium. Owner D3 with A2. Medium. See G2.

What works: front matter goes into metadata, not the text; setext and ATX headings, hard breaks, reference links, autolinks, and image alt text are right; code blocks stay in the text and are skipped in narration by default with "code block skipped"; the structured table narration speaks header names with values.

### Data safety and robustness

**D1. Quitting in edit mode after a save stores positions on the old text.** High. Owner D3. Small; patch S5.
- Evidence: `quit` calls `finish_leave(false, false)` when edit mode is clean (`edit.rs:1448-1453`), so a session that saved restores the reading text from before the edits and maps bookmarks, notes, and the cursor into it; `shutdown` saves them. Reproduced by the patch's test: a bookmark on "The end" came back at char 20 instead of 62 after reopening.
- Fix: pass the session's `maps_stale()` as `rebuild`.

**D2. Files changed on disk while open are not detected.** Medium-high for anyone who also edits in Obsidian or VS Code, or runs `git pull`. Owner C (`textweaver-editor`) and D3. Small to medium.
- Evidence: nothing records a file's modification time or size on open or save (`crates/textweaver-editor/src/session.rs:282-304` saves unconditionally), so Ctrl+S overwrites changes made elsewhere. Recovery puts a snapshot over whatever the file holds now (`edit.rs:1408-1431`).
- Fix: record modification time, size, and a hash on entering Edit mode and after each save; before saving, compare and offer overwrite, reload, or Save As.

**D3. Binary and non-UTF-8 files open as text.** Medium. Owner A2. Small to medium.
- Evidence: an unknown extension falls back to the text loader (`crates/textweaver-formats/src/lib.rs:205-213`), and bytes are decoded lossily (`:238-242`). A `.docx` or `.pdf` without its loader is read aloud as garbage; UTF-16 (PowerShell 5.1 `>` output) has a NUL after every letter and reads letter by letter; Windows-1252 smart quotes become replacement characters. Saving such files in place is now refused (commit `0366d6c`).
- Fix: sniff the first 8 KB (NULs, a high share of invalid bytes) and refuse with a clear message; decode UTF-16 by its byte-order mark and Windows-1252 with `encoding_rs` (already a workspace dependency), and remember the encoding so Save can write it back.

**D4. Corrupt settings, keymap, state, and recent files.** Fixed. A corrupt `settings.toml` is backed up and announced, and a bad `keymap.toml` is ignored and announced. Corrupt per-document state and `recent.json` used to be overwritten; they are now set aside (commits `6a54494`, `e8f5870`). What remains: nothing tells the user a file was set aside, because nothing is logged (D5).

**D5. Nothing is logged, and some failures are only logged.** Medium. Owner D3 (TUI and CLI). Small.
- Evidence: no logger is installed anywhere (no `set_logger`, `env_logger`, or `simplelog` in the workspace), so every `log::warn!` is lost. Only logged: a failed position save (`app.rs:474-476`, `:728-730`), a failed recent-files save (`app.rs:456`), a document out of step with the editor (`edit.rs:715`), a failed notes save (`crates/textweaver-app/src/notes.rs:582-585`). Adding a bookmark says "Bookmark ... set at ... percent" even when saving it failed (`crates/textweaver-app/src/marks.rs:150-153`).
- Fix: a small file logger under the data folder (`textweaver.log`, last few runs), and announce a failed save of notes or bookmarks once.

**D6. A panic leaves the position unsaved and bracketed paste on.** Low. Owner D3. Small. `ratatui::init` restores the terminal on panic, but `shutdown` does not run (no position save) and bracketed paste stays enabled (`crates/textweaver-tui/src/lib.rs:84-90`). A panic hook that writes an emergency snapshot and saves the position would close the gap.

What is fine: I found no `unwrap` or `expect` reachable from user input in the reader, editor, store, or TUI; positions saved for a longer version of a file are clamped; empty patterns, invalid regular expressions, and zero-width matches are handled; Backspace at the start and Delete at the end give an earcon and a message; all writes go through a temp file, fsync, and rename.

### Platform independence

**X1. AltGr characters cannot be typed on Windows with non-US layouts.** Medium. Owner D3. Small.
- Evidence: crossterm reports AltGr as Ctrl+Alt, and the TUI inserts a character only without Ctrl and Alt (`crates/textweaver-tui/src/ui.rs:254`, and the prompt at `:404`). On German, French, or Nordic layouts `[ ] { } \ | @ ~` cannot be typed, and Markdown links and code need them.
- Fix: when no binding matches, insert a Ctrl+Alt character that is not an ASCII letter.

**X2. Paths.** Low. Document keys go through `resolve_path`, so a file reached by a link, a short name, or another letter case keeps one key; recent entries now do too (commit `ccae825`). Network paths keep the `\\?\UNC\` prefix, which is shown and spoken (`crates/textweaver-store/src/library.rs:80-88`); changing it would change existing document keys on network shares, so it needs a small migration. Owner C.

**X3. Line endings and BOMs.** Fixed. CR never reaches the rope; CRLF, lone CR (commit `3663873`), and the UTF-8 BOM are kept on save.

**X4. CI gaps** (`.github/workflows/`).
- Fixed on this branch: wave and integration branches had no CI on push, and Windows and macOS built no features.
- The GUI is excluded everywhere (expected until Agent K's workflow lands).
- The 32-bit engine hosts are built but not tested; the real-engine tests (Voxin in Docker, SAPI voices) never run in CI.
- There is no Docker job, although Docker parity is expected.
- Tests run only in debug builds, so release-only behavior (integer overflow wraps) is untested; Windows release packages are built by hand.
- `apple.yml` runs only on `agent/f-apple`; `release.yml` builds only macOS.
- The TUI tests bypass crossterm's Windows key parsing, so AltGr and Alt codes are never exercised.
- Nothing runs the benchmark; `cargo xtask bench --quick` takes a few minutes and could run weekly.
- A flaky test: `type_format_undo_save_and_reopen_through_keys` (`crates/textweaver-tui/tests/edit.rs:180`) failed once in Docker while the machine was busy and passed three times after. Its `settle()` waits a fixed 200 ms for the echo to reach the recording backend; waiting until the expected utterance arrives (as `tests/edit.rs` in the app does with `wait_until`) would make it reliable. Owner D3. Small.

### Gaps: promised or stored, but not working

**G1. Actions that say "not available yet".** See A1 and A2: `ToggleCharacterKeys`, the four select actions, `ReadParagraph`, `ChooseVoice`, `OpenLibrary`. The JSON-RPC `read paragraph` quietly maps to replay paragraph (`crates/textweaver-app/src/rpc.rs:576`).

**G2. Settings stored but never used.**
- `normalization.table_mode`: the app's narration policy never reads it (`playback.rs:159-165`), so tables are always read structured. Patch S6.
- `normalization.footnote_mode`: never read; the app loads with `LoadOptions::default()` (`app.rs:441`, `edit.rs:513`, `:525`, `:1412`), which defers footnotes, whatever the setting (default Inline).
- `highlight.color`, `highlight.sentence_color`, `speech.favorite_voices`: never read.
- `tw migrate-star` imports Star's footnote mode and sentence color (`crates/textweaver-store/src/migrate/star.rs:302`, `:355`), so migrated preferences are silently ignored.

**G3. CLI stubs.** `tw convert` prints "not implemented" (`crates/textweaver-cli/src/cmd/convert.rs:24`) while `--help` lists its options; Agent L owns it. The GUI binary prints "not built yet" (Agent K).

**G4. Markdown authoring features a Star user relies on that have no action yet.** Follow a link or say its address (the Link marker already stores it); jump from a footnote reference to its note and back; move by table row and cell and hear the column header; move to the next heading of a given level; word count; spell check (`docs/star-gaps.md`); clipboard copy and cut in Edit mode (there is no clipboard code, and Ctrl+C in Edit mode does nothing); a voice chooser; changing verbosity and punctuation at run time.

**G5. Documentation promises.** README and CHANGELOG (alpha.3) promise switchable single-key shortcuts and highlighting the selection; `docs/keyboard.md` lists Shift+arrows, Shift+S, Alt+V, and Alt+L. All work once patch S2 lands, except Alt+V and Alt+L.

**G6. No guide to using the terminal reader with a screen reader.** Medium. Owner: docs. Small. Nothing says whether to run with self-voicing or `--no-speech` under JAWS or NVDA, how to avoid hearing announcements twice (the screen reader reads the status line while textweaver also speaks it), or which terminal settings work (Windows Terminal versus conhost). Jon's own setup would make a good first page.

### What a GUI still needs from the app core

Briefly, each medium and owned by D3 unless noted:
- A view model: line wrapping and window slicing live in the TUI (`crates/textweaver-tui/src/layout.rs:96`); the app offers only `viewport()` and `highlights(range)` (`crates/textweaver-app/src/view.rs:186`). A `visible_rows(width, height)` with highlight spans belongs in the app.
- UTF-16 ranges: `Document::display()` exists (`crates/textweaver-text/src/document.rs:215-218`), but focus, highlights, and JSON-RPC notifications are char offsets.
- A way to wake the GUI: speech arrives only through `poll_speech` and `tick`. A callback or a channel the GUI can select on (the JSON-RPC server already builds its own).
- Threading: `Announcer` has no `Send` bound (`crates/textweaver-a11y/src/lib.rs:133`), so `App` must stay on one thread. That suits wxWidgets, but say so in the API.
- List and prompt state (selected item, announcements of list moves) live in the TUI (`ui.rs:302-350`, `widgets.rs`); a GUI would duplicate them.
- Edits from a native text control: there is no "replace this range with this text" command, only caret-based `Insert`, `DeleteBack`, and `DeleteForward`.

## Benchmark harness

`cargo xtask bench` rebuilds xtask in release mode with the `bench` feature and runs every measurement on:
- `fixtures/sample.md`, `README.md`, and `docs/star-parity.md` (220 KB of real Markdown);
- generated corpora in `target/bench-corpus/`: `md-1mb.md` and `md-10mb.md` (headings, paragraphs, lists, tables, code, quotes, footnotes, front matter), `list-50k-lines.md` (one tight list of 50,000 items), and `one-line-1mb.txt` (a 1 MB single line).

Options: `--quick` (skip the 10 MB corpus, about two minutes), `--only NAME`, `--file PATH` (repeatable, your own documents), `--json PATH`. Each line of the report is one number, so it reads well with a screen reader. Nothing is played: the speech backend is a silent clock that records when it would start speaking. Peak heap comes from a counting allocator in the bench process.

What "keystroke to speech" means: from the dispatch of the key's command to the moment a backend is asked to speak the result (announcement or reading). It includes the speech thread's handoff and normalization, not the engine's own start-up or audio latency.
